# Shenlong Test Suite

Canonical regression suite for Shenlong's reasoning pipeline (intent classification, contextual retrieval, memory, proactive nudges, confidence handling, calendar date resolution). Created 2026-08-03 during the Shenlong Intelligence pass. **This is a living document** — extend it whenever Shenlong's pipeline changes; don't let it drift out of date with the code.

## Methodology

Two validation tiers, and every result below says which one it got — never blend them:

- **LOCAL** — executed directly against real code in a real browser (Playwright, `preview` skill), with zero network mocking beyond intercepting `/api/gemini/assistant` itself (to inspect the outgoing payload without needing a live key). Covers: `classifyIntentDomain()`, `rememberFact()`/dedup/eviction, `proactiveNudge()`, the local deterministic parser (`parseLocal()`), and the exact context payload `askGemini()` constructs. All of this is deterministic, non-LLM code — a LOCAL result is a real pass/fail, not a simulation.
- **LIVE** — requires an actual round-trip through Gemini (reasoning quality, confidence self-assessment accuracy, hallucination avoidance in practice, clarification quality). **No live `GEMINI_API_KEY` was available in the local dev environment for this pass** (`proxy/.env` has none configured), and this pass's code had not yet been deployed anywhere at the time this suite was written — testing against the live production URL would have validated the *previous* version of Shenlong, not this pass's changes, which would have been dishonest. Cases requiring LIVE validation are included below with their expected behavior fully specified, status marked `NOT YET LIVE-TESTED`, and a note on exactly what to run once this pass is deployed.

Run the LOCAL suite yourself: `.claude/skills/preview/SKILL.md` (`node .claude/skills/preview/drive.mjs --page index --script <flow>`) — the flow used to produce the results below is reconstructable from the "How to reproduce" section at the bottom of this file.

## Bugs found and fixed by this suite (before it ever shipped)

| # | Bug | Found by | Fix |
|---|---|---|---|
| 1 | `classifyIntentDomain()` misclassified gym/health questions as `'multi'` because `today`/`tomorrow`/`tonight`/`weekend` were treated as calendar-specific keywords, when they're generic time modifiers used in every domain. | TS-01, TS-02, TS-05 | Removed those words from the calendar pattern. |
| 2 | Wardrobe classification missed common garment words entirely ("jackets", "shirts", etc. weren't in the pattern) and, separately, a first attempt at fixing this introduced "top"/"tops" — which collides with this app's own gym terminology ("log today's **top** set"). | TS-04 (design review before it shipped) | Added garment/category words; deliberately excluded "top"/"tops". |
| 3 | `rememberFact()`'s duplicate check used substring containment (`a.includes(b)`), so "fact number 1" false-positived as a duplicate of "fact number 10" through "fact number 19". | TS-11 | Switched to exact match (case-insensitive) only. |
| 4 | **Pre-existing, not introduced by this pass**: the local parser's water/food branches had no question-detection guard, so "how much water so far" (a question) was silently parsed as `log_water` (a command) and would have logged a phantom serving with zero confirmation. | TS-19 (discovered while testing contextual retrieval) | Added an `isQuestion` guard (`^(how|what|did|have|has|when|is|are|do|does)\b` or trailing `?`) before both branches. |

## Known limitations (honest, not swept under the rug)

- **No live Gemini validation performed in this pass.** Local dev has no `GEMINI_API_KEY`; the code hadn't been deployed anywhere at the time this suite was written. TS-25–29 need a real run once deployed.
- **Wardrobe grounding is item-counts-only.** No live weather feed exists (`[[Roadmap]]` "Wardrobe weather input" is still a placeholder), so Shenlong is explicitly instructed never to judge an outfit as too warm/cold — it can only report what's in the closet, not whether it's appropriate for the day.
- **No true multi-turn memory.** Each message is classified and answered independently; "make it 6pm" after "add gym at 5pm" relies entirely on the calendar's own fuzzy title-matching (pre-existing), not on Shenlong remembering the prior exchange. Only *explicit, durable* facts (`remember_fact`) persist across turns — ordinary conversation is not retained.
- **"next Friday" == "this Friday"** when today isn't Friday (TS-24) — a deliberate, documented simplification, not a bug, but worth knowing if it ever surprises someone.
- **Ambiguous calendar-event deletion (Known Issue #24)** is untouched — ambiguity handling in this pass covers the Gemini reasoning path, not the pre-existing deterministic `findEvent` matcher.

## How to reproduce the LOCAL results

1. `npx serve . -l 5055` from the repo root.
2. Playwright (`preview` skill) against `--page index`, seeding `localStorage` per case as shown in the "Actual behaviour" column, then either calling `window.classifyIntentDomain()`/`window.rememberFact()`/`window.proactiveNudge()` directly, or driving `#aiForm`/`#aiInput` for end-to-end parser cases, with `/api/gemini/assistant` intercepted via `page.route()` to capture the outgoing payload without needing a live key.
3. For TS-24 (weekday math), the algorithm was additionally verified in isolation via direct `node -e` execution against a fixed, known date — see the dev journal entry for this pass for the exact script.
